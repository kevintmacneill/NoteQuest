# M6 avatar art adapter — foundation only

This packet supports the independently tracked M6 UI draft (#158), but does not activate it, publish art, or establish a new style. The three-pose painted approval gate remains open. The module returns an adapter compatible with the builder's ready/draw/swatch/silhouette interface once a complete owner-approved manifest is supplied.

## Authoring contract
- Three fixed pose IDs: front, wave, walk. Use approved aligned transparent 512 × 512 WebP layers; separate lower-resolution exports can be prepared for later optimization. Every layer in a pose uses the same origin, dimensions and anchors. A common portrait crop is explicitly supplied by the approved manifest.
- For each body and pose, enumerate the engine catalog's skin, outfit, hair style × hair color, and accessory IDs, with **hair back → accessory back → body → outfit → hair front → accessory front** composition order. Hair and accessory entries are `{back,front}`; explicit `null` means an unused plane, not a missing asset. At least one plane must be nonempty. No filename construction from saved learner data. No accessory layer for acc-none. This conservative first version uses painted variants, not unapproved hue shifts. Long hair, hats and backpacks can now use front and rear planes without painting them into the body or clothing. Each option has a separate painted swatch in `swatches` (hair grouped by body); changing a choice never composites all of the available options. The manifest must contain a neutral painted silhouette.
- Registry status must be approved, version must equal the engine catalog, and every required entry must pass the local-WebP path allowlist. In the production integration PR, add filesystem validation of every path, real image dimension/alpha checks, and visually compare the actual composites. Setting status alone is not artwork approval. No production manifest is included.
- Composition uses a bounded 32-entry promise/blob cache keyed by look and pose. Concurrent requests share a composition, failures are evicted, and target revisions prevent stale async replacement. A portrait crops the front composite; no per-frame layer stack. Object URLs are short-lived and revoked even on decode failure. Composite failure draws the approved silhouette if possible, then rejects so the builder does not mistake a fallback for a successful preview.
- No game save, learner identity, route, music, or engine mutation. Builder draft choices can be rendered locally; persisted learner portraits must use the engine's displayLook query. Production integration must use theme tokens, check reduced-motion, handle missing art with the neutral silhouette, preserve building pointer events and verify the five viewports. Propose a single approved walk pose with a subtle CSS bob and translation for Phase 1; reduce-motion disables the bob. True alternating walk frames are a later, independently approved artwork increment. This proposal is not animation or art approval; no motion changes in this PR. Do not enable the builder until the full catalog and approved visual samples are ready (superseded on 2026-11-26 by the partial rollout below).

Tests are synthetic (no published image assets); real browser/rendering and physical device acceptance remain mandatory.

## Partial approved manifests (owner decision 2026-11-26)
Kevin chose a partial rollout: new learners get the builder now, with whatever art is approved, and each newly approved batch is merged to main.
- `scope: "partial"` with `status: "approved"` and a named `approvedBy`. Only painted entries are listed. An unlisted choice is **coming soon**, not an error. Every listed entry must be a catalog ID with a valid path or plane. Each body needs at least one complete look in the front pose. Art is painted front pose first, so availability is decided by the front pose; a wave or walk draw of a look whose pose isn't painted yet uses the front pose instead. `silhouette` is optional; when it's absent, a failed draw leaves the slot empty. Any other `scope` value is rejected.
- The adapter adds `partial`, `choose(look, field, id)` (the look after that choice, adjusting unlocked parts to painted ones, or `null` when the choice isn't painted yet) and `fit(look)`. The builder greys out choices that `choose` rejects. Arrows, swipes and Surprise Me only land on painted choices.
- A missing swatch for a painted choice shows the painted look itself (a head crop, or the whole figure for outfits). It never shows a recolor or a placeholder.
- During a partial rollout, existing learners keep their original picture and aren't sent to the builder; only learners with a saved look get painted portraits and the edit buttons.

## Several accessories and outfit-matched variants (owner decisions 2026-11-26)
- **Several accessories:** looks carry `accessories` (engine 1.9.0, one per spot). `layers()` draws hair back, then every accessory's back plane, then skin, outfit and hair front, then every accessory's front plane. Accessories go in spot order: back, chest, neck, face, head. `choose(look, 'accessory', id)` toggles: None clears all, a worn one comes off, and a new one replaces whatever is in its spot.
- **Outfit-matched variants:** an accessory entry may be `{byOutfit: {<outfit>: plane}}` instead of a single plane (goggles). It's drawn with the current outfit's variant, and it's available only for outfits that have one. A complete manifest needs every outfit. A partial manifest may list any painted subset of real outfit IDs.
